# 🎧 Spotify "Smart Queue" A/B Test: Reproducible Experimentation Pipeline

End-to-end product analytics project: a simulated A/B test of a "Smart Queue" feature (an interactive 3-choice "Next Recommended Songs" banner) on a Spotify-style app. It covers the full workflow from business question to launch recommendation: metrics, tracking plan, power analysis, pre-registration, data simulation, SRM validation, BigQuery aggregation, hypothesis testing, and a Mixpanel dashboard.

> [!NOTE]
> **All user data is simulated.** Baselines and effect sizes are stated assumptions, so the results demonstrate the method and tooling, not a real-world finding. The business, presentation, and decision narrative lives in the experiment document; **this README is the technical guide for reproducing every step with the code in this repo.**

## 🚀 Reproduce it, step by step

### 0️⃣ 🎵 Try the live mockup
- **Live app:** [https://spotify-smart-queue-mockup.vercel.app/](https://spotify-smart-queue-mockup.vercel.app/)
- Use the **Control / Treatment** toggle in the header. Treatment shows the Smart Queue banner with 3 song choices; the event log at the bottom shows tracking-plan events firing as you click.
- Optional, run locally from the repo root:
  ```bash
  npm install
  npm run dev        # http://localhost:3000
  ```
- `lib/analytics.js` marks the single place where a real Mixpanel/GA4 SDK call would plug in.

### 1️⃣ 📖 Read the experiment document
- **Experiment document:** [https://app.notion.com/p/Spotify-Smart-Queue-Feature-A-B-Test-Experiment-Document-3f6f9fe7805d80c68c15e2c5daba1b96?showMoveTo=true&saveParent=true](https://app.notion.com/p/Spotify-Smart-Queue-Feature-A-B-Test-Experiment-Document-3f6f9fe7805d80c68c15e2c5daba1b96?showMoveTo=true&saveParent=true)
- Read the Background, Business Questions, Metrics Framework, Baselines, Power Analysis, and Hypothesis Framework sections first. The test selection and decision rules were **pre-registered before any data existed**.

### 2️⃣ 🧭 Review the tracking plan
- **Tracking plan:** [https://alpine-donkey-0c0.notion.site/Tracking-Implementation-Plan-3f6f9fe7805d807bb79bdfb582966b8d?pvs=73](https://alpine-donkey-0c0.notion.site/Tracking-Implementation-Plan-3f6f9fe7805d807bb79bdfb582966b8d?pvs=73)
- It defines the events and properties the app should emit (`session_start`, `smart_queue_shown`, `smart_queue_track_selected`, `media_stream_heartbeat`, `app_session_error`).
- The simulation rolls these up into **one daily `app_session_summary` record per user** instead of emitting every raw event.

### 3️⃣ 🛠️ Set up your environment
```bash
git clone https://github.com/wacsvn/spotify-smart-queue-ab-test.git
cd spotify-smart-queue-ab-test
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 4️⃣ ⚡ Run the power analysis
Open `analytics/hypothesis_testing.ipynb` (select the `.venv` kernel) and run the **Power Analysis** section.

| Input | Value |
|---|---|
| Baseline | 840 min / user / week |
| Standard deviation | 360 min |
| MDE | 2% (+16.8 min) |
| Alpha / Power | 0.05 / 0.80 |

✅ **Expected:** Cohen's d = 0.0467, **7,210 users per variant (14,420 total)**.

### 5️⃣ 🎲 Simulate the experiment data
```bash
python analytics/data/data_simulation.py
```
Writes `analytics/data/simulated_experiment_log.csv`. The generator is seeded (`SEED = 42`), so you should get the same dataset every run. It models, in order:

1. **Assignment:** independent random draws into Control / Treatment
2. **Compliance:** 40% of Treatment users ever use the banner; Control has no access
3. **User heterogeneity:** per-user baseline multiplier, so weekly SD is about 360
4. **Daily behavior:** search and autoplay minutes around 840 min/week
5. **Treatment effect (compliers only):** extra banner minutes, partly replacing autoplay, with a novelty bump in weeks 1-2 that settles by week 3
6. **Churn and crashes:** W4 retention and crash rates per variant

Columns: `user_id, variant, is_complier, experiment_day, search_minutes, search_sessions, autoplay_minutes, smart_queue_minutes, total_minutes, crashes, w4_active_day`

✅ **Expected:** 398,080 rows, 14,420 users (Control 7,135 / Treatment 7,285), ITT lift about +26.6 min/week.

### 6️⃣ 🔍 Validate the dataset (SRM check)
Back in the notebook, run the **Dataset Validation** section. It runs a chi-square goodness-of-fit test on the user split, using the strict industry threshold of p < 0.001 to flag pipeline failures.

✅ **Expected:** chi-square = 1.5603, p = 0.2116, **no Sample Ratio Mismatch**.

### 7️⃣ 🗄️ Aggregate metrics in BigQuery
1. Open the [BigQuery console](https://console.cloud.google.com/bigquery) (sandbox mode needs no billing).
2. Create a dataset named `Spotify_AB_Simulated_Traffic_Data`.
3. Create a table `raw_traffic_log` by uploading `analytics/data/simulated_experiment_log.csv` (auto-detect schema, 1 header row).
4. Run `analytics/sql/experiment_summary.sql`. If your project or dataset names differ, edit the fully qualified table name in the query.

The query collapses daily rows into **user-level weekly averages** (28-day totals / 4), then summarizes by variant. Crash rate is per user-day row (a proxy for per-session), and W4 retention is any activity on days 21-28.

✅ **Expected:**

| variant | users | mean weekly min | std | autoplay min | search sessions | crash rate % | W4 retention % |
|---|---|---|---|---|---|---|---|
| control | 7,135 | 834.55 | 359.72 | 625.96 | 16.68 | 0.206 | 95.21 |
| treatment | 7,285 | 861.16 | 370.62 | 617.53 | 16.70 | 0.213 | 94.95 |

### 8️⃣ 🧪 Run the pre-registered hypothesis tests
In the notebook, run the **Results Analysis** section top to bottom (it reads `analytics/data/simulated_experiment_log.csv`).

| Test | Purpose |
|---|---|
| Welch's t-test + 95% CI | Primary OEC: weekly streaming minutes per enrolled user (ITT) |
| One-sided non-inferiority (z) | Guardrail: W4 retention, margin -1pp |
| Halt rule (z) | Guardrail: crash rate, threshold +0.05pp |
| Welch + Holm correction | Secondary: autoplay minutes, search minutes, search sessions |
| Wald estimator + bootstrap | CACE: effect among users who actually use the banner |
| Weekly lift + paired decay test | Novelty effect: does the lift shrink over 28 days? |

Outputs include the decision printout and `analytics/figures/results_summary.png`.

✅ **Expected:** primary lift **+26.6 min/week (+3.19%), p = 1.2e-05**; both guardrails pass; decision **LAUNCH**. Full table below.

### 9️⃣ 📈 Import to Mixpanel and build the dashboard
1. Create a free [Mixpanel](https://mixpanel.com) project and copy the **Project Token** (Project Settings). Note the project's **data residency**: US uses `api`, EU uses `api-eu`, India uses `api-in`.
2. Set credentials as environment variables. **Never commit your token.**
   ```bash
   export MIXPANEL_TOKEN="your-project-token"   # PowerShell: $env:MIXPANEL_TOKEN="..."
   export MIXPANEL_REGION="api"                 # api | api-eu | api-in
   ```
3. Dry run, which builds and validates all events and sends nothing:
   ```bash
   python analytics/mixpanel_import.py --start-date 2026-09-09 --dry-run
   ```
4. Send one test batch, which must print `imported 2000`, then check Mixpanel Insights:
   ```bash
   python analytics/mixpanel_import.py --start-date 2026-09-09 --limit 2000
   ```
5. Run the full import (add `--event-name app_session_summary_v2` to match the published dashboard):
   ```bash
   python analytics/mixpanel_import.py --start-date 2026-09-09
   ```
6. **Reconcile with BigQuery:** unique users by `experiment_variant` should be 7,135 / 7,285 and total events 398,080.
7. **Build the monitoring dashboard** (free plan allows 5 saved reports): SRM bars (uniques by variant), average streaming minutes per user, autoplay minutes by variant, W4 retention, and Smart Queue adoption (uniques with `smart_queue_minutes > 0` divided by treatment uniques).

> [!TIP]
> The script uses Mixpanel's `/import` endpoint (not `/track`) so events keep their backdated timestamps. `$insert_id` makes reruns idempotent, and strict mode returns per-event errors plus a confirmed imported count. One full import is about 398k events, well within the free tier's 1M/month.

## 🧯 Troubleshooting

| Problem | Fix |
|---|---|
| Notebook can't find the CSV | Notebook paths are relative to `analytics/`. Open the notebook from there, and run Step 5 first if the CSV is missing. |
| Numbers differ slightly from the table | Confirm `SEED = 42` is unchanged and compare your NumPy/pandas versions (`pip list`). Small version differences can shift the last digits. |
| BigQuery "table not found" | Use the fully qualified name `project.dataset.table` in the SQL. |
| Mixpanel import "works" but no data appears | Check the project's data residency against `MIXPANEL_REGION` and the token against the project you're viewing. The script prints Mixpanel's confirmed imported count per batch. Allow a few minutes. |
| First or last dashboard day looks partial | Events are stamped in UTC but Mixpanel buckets days in the project timezone. Trim the date range by one day on each end. |

## ⚠️ Limitations

- **Simulated data:** compliance (40%), effect size, novelty profile, crash and retention rates are assumed inputs, not findings.
- **Adoption is held constant** across the 28 days; novelty is modeled in minutes only.
- **Crash rate is per user-day,** a proxy for the pre-registered per-session rate.
- The simulation emits one daily rollup event per user, not every raw tracking-plan event.
